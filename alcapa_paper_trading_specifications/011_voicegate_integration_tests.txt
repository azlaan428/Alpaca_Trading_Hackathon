1.1. Abstract
This document specifies the integration-test tier of VoiceGate's testing pyramid
(008_voicegate_testing.txt Section 1.7), exercising two or more `src/voicegate/` engine
modules together to prove that unit-verified behaviors compose correctly across module
boundaries, for one gauntlet phase transition at a time.

1.2. Key Words
integration test, module boundary, gauntlet phase transition, cross-module behavior,
fixture, pytest, patch adviser re-run.

1.3. Executive Summary
Where 009_voicegate_unit_tests.txt proves each engine module correct in isolation, this
document proves that combinations of modules — `call_orchestrator` driving
`transcription_engine` and `compliance_scoring_engine`, `compliance_scoring_engine` feeding
`verdict_engine`, a Fail verdict feeding `patch_adviser` and triggering a re-run — behave
correctly together, using the same seeded, deterministic fixtures established at the unit
tier.

1.4. Key Findings
1.4.1. Integration tests operate on at least two `src/voicegate/` modules per test case,
distinguishing them from the single-module scope of 009_voicegate_unit_tests.txt.
1.4.2. One full gauntlet phase transition (e.g. Intent Discovery -> Resolution Attempt),
exercised end-to-end at the module level, is the primary integration surface — short of full
UI involvement, which is covered by 013_voicegate_end2end_testing.txt.
1.4.3. Transcription feeding into compliance scoring, and a Fail verdict feeding into the
`patch_adviser` and a subsequent re-run, are the two most consequential cross-module chains
and receive dedicated test coverage.
1.4.4. Guardrail resistance (prompt injection, actor/role confusion) is treated as an
integration concern in addition to a unit concern, since a transcript fixture must survive
the full `transcription_engine` -> `compliance_scoring_engine` -> `verdict_engine` chain
without the embedded instruction or swapped role taking effect anywhere along it.
1.4.5. Integration tests reuse the seeded `rng_service` fixtures from
009_voicegate_unit_tests.txt Section 1.6.9 rather than redefining new randomness handling.

1.5. Philosophical Preamble
A correct set of parts does not guarantee a correct machine. Integration tests exist because
a compliance verdict is only trustworthy if the engines that produce it actually agree with
each other once wired together, not merely each individually correct in a vacuum
(001_voice_transcription_concept.txt Section 1.5).

1.6. Integration Test Scope

1.6.1. Gauntlet Phase-Transition Integration
A single phase transition (e.g. Greeting -> Intent Discovery, or Compliance Check ->
Wrap-up), executed end-to-end at the module level, produces the exact combination of state
changes expected across `call_orchestrator`, `transcription_engine`, and `event_log`.

1.6.2. Transcription-to-Scoring Integration
A transcribed dual-channel exchange produced by `transcription_engine` is correctly consumed
by `compliance_scoring_engine`, which returns a score referencing the correct
`statutory_rules`/`company_terms_snapshots` fixture entries for that exchange's content.

1.6.3. Persona/Scenario-to-Orchestrator Integration
A given persona/scenario selection (`persona_engine` + `scenario_engine`) correctly drives
the simulated caller's behavior through `call_orchestrator`'s phase sequencing, using the
seeded `rng_service` for reproducible variance.

1.6.4. Scoring-to-Verdict Integration
A `compliance_scoring_engine` output correctly resolves, via `verdict_engine`, to Pass,
Fail, or Flag with the correct rule citation attached; a borderline score is not silently
rounded to Pass.

1.6.5. Fail-to-Patch-Adviser-to-Re-Run Integration
A Fail verdict correctly invokes `patch_adviser`, which proposes a system-prompt patch; the
gauntlet is re-run (a new, separately logged run, per 009_voicegate_unit_tests.txt Section
1.6.10) against the patched configuration to verify the fix, without the original patch being
auto-applied without human confirmation.

1.6.6. Guardrail Cross-Module Resistance
A transcript fixture containing an embedded instruction, or a deliberately mislabeled
speaker channel, is exercised through the full `transcription_engine` ->
`compliance_scoring_engine` -> `verdict_engine` chain and asserted to have no effect on the
returned verdict at any point in the chain, extending the unit-tier guardrail cases
(009_voicegate_unit_tests.txt Sections 1.6.11-1.6.12) to the cross-module level.

1.7. Test Environment and Fixtures
1.7.1. Integration tests run against an in-memory instantiation of the full
`src/voicegate/` module set, with no external network dependency and no live call against a
production voice agent — sandbox/mock target agents only, per 015_voicegate_deployment.txt.
1.7.2. Fixtures use the smallest supported scenario/persona catalog subset by default to keep
integration tests fast, reserving larger-sample runs for 012_voicegate_performance_tests.txt.

1.12. Conclusion
Six cross-module integration-test scopes give VoiceGate confidence that its correctly
unit-tested engines also cooperate correctly across one gauntlet phase transition at a time,
ahead of full end-to-end validation in 013_voicegate_end2end_testing.txt.
