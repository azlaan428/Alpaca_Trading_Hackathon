1.1. Abstract
This document specifies the logging standards for VoiceGate, carrying forward the original
".LOG formatting" baseline directive into a structured logging contract used by the Python
`logging` module (voice_processing_specifications/005_voicegate_coding_standards.txt §1.9)
and consumed as the source of truth for run statistics
(voice_processing_specifications/010_voicegate_run_statistics.txt) and verdict auditability.

1.2. Key Words
logging, .LOG format, log level, structured log entry, event log, verdict event, guardrail
trigger, statistics source, VoiceGate.

1.3. Executive Summary
VoiceGate writes structured, human-readable `.LOG` files via the Python `logging` module
exclusively (never `print()`), at standard severity levels, with every gauntlet-run-relevant
event (call start, persona/scenario draw, transcript turn, compliance-scoring result, verdict,
guardrail trigger) also captured as a structured entry in the run event log
(`src/voicegate/event_log`), which doubles as the source of truth for run statistics and for
the Risk Report's audit trail.

1.4. Key Findings
1.4.1. `.LOG` files remain the required output format for all logging, per the preserved
baseline directive in Section 1.6.
1.4.2. Development runs log at `DEBUG` level and above; production/scheduled gauntlet runs log
at `INFO` level and above.
1.4.3. Every state-mutating event in a gauntlet run (persona assignment, scenario draw,
transcript turn, compliance-scoring evaluation, verdict issuance, patch-adviser suggestion)
produces exactly one structured event-log entry, consumed by
voice_processing_specifications/010_voicegate_run_statistics.txt.
1.4.4. Guardrail triggers (prompt-injection attempt detected in transcript content, judge-model
actor/role-confusion flag) are logged with an explicit marker distinguishing them from ordinary
scoring events, per Section 1.10.
1.4.5. Logging never uses `print()` statements anywhere in the codebase, per
voice_processing_specifications/005_voicegate_coding_standards.txt §1.9.

1.5. Philosophical Preamble
A log is a promise that nothing important happened invisibly. In a compliance test bench this
promise is load-bearing: a Risk Report's Pass/Fail/Flag verdict is only as trustworthy as the
event trail behind it. The `.LOG` baseline directive, preserved verbatim below, is expanded
into a full contract so that logging serves diagnostics for engineers and the auditable
evidence chain that Call Review and Risk Report both depend on.

1.7. Log File Format and Location
1.7.1. Log output uses the `.LOG` file extension, per the preserved baseline directive.
1.7.2. Each log line includes, at minimum: ISO 8601 timestamp, log level, module/logger name,
and message, formatted via the Python `logging` module's standard formatter configuration.
1.7.3. Log files are written to a dedicated local `logs/` directory, rotated per gauntlet run
or by size, to avoid unbounded growth during extended test-bench sessions.

1.8. Log Levels and Usage
| Level | Usage |
|-------|-------|
| DEBUG | Detailed internal state useful only during development (development runs only) |
| INFO | Normal run events: call start/end, persona/scenario draw, transcript turns, verdicts |
| WARNING | Recoverable anomalies (e.g. a transcription gap, a retried API call) |
| ERROR | Unexpected failures that do not crash the run (e.g. a single scoring-engine exception) |
| CRITICAL | Failures that prevent the gauntlet run from continuing |

1.9. Structured Log Entry Contract
Each run-relevant log entry additionally captures, in a structured (not free-text-only) form:
call/run identifier, event type (call_started, persona_assigned, scenario_drawn,
transcript_turn, verdict_issued, patch_suggested; per
voice_processing_specifications/006_voicegate_scaffolding.txt module list), scenario/persona
identifiers, and outcome (e.g. `verdict: FLAG, rule_id: EU-AI-ACT-ART50`), enabling
voice_processing_specifications/010_voicegate_run_statistics.txt to derive statistics directly
from the log rather than a separate, parallel tracking mechanism. Example verdict-event entry:
`INFO 2026-08-03T14:02:11Z verdict_engine call_id=run-042 event=verdict_issued
outcome=FLAG rule_id=CA-SB243 clause=disclosure`.

1.10. Guardrail and Debug-Action Log Marking
Every guardrail trigger (prompt-injection attempt in caller/transcript content, judge-model
actor/role-confusion flag) is logged with an explicit `guardrail_triggered: true` structured
field, and every debug/dry-run action is logged with `is_debug_action: true`, ensuring neither
is silently conflated with a genuine scored gauntlet event in statistics or the Risk Report.

1.11. Summary Table
| Aspect | Rule |
|--------|------|
| File format | `.LOG` (preserved baseline) |
| Output mechanism | Python `logging` module only, never `print()` |
| Levels | DEBUG, INFO, WARNING, ERROR, CRITICAL |
| Structured fields | Run/call id, event type, scenario/persona id, verdict + rule id |
| Guardrail marking | Explicit `guardrail_triggered` field on injection/confusion-flag entries |
| Debug marking | Explicit `is_debug_action` field on non-scored dry-run entries |

1.13. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Free-text-only logging making statistics/Risk Report derivation unreliable | Medium | High | 1.9 mandates structured fields on every run-relevant entry |
| Guardrail/debug events polluting genuine verdict statistics | Low | Medium | 1.10 mandates explicit markers, filtered out downstream |
| Unbounded log file growth during long gauntlet sessions | Low | Low | 1.7.3 mandates rotation by run or size |
