1.1. Abstract
This document specifies performance-tier tests for VoiceGate: per-command latency budgets,
full-gauntlet-run throughput, scenario-catalog scaling behavior, persistence latency, and a
large-sample guardrail load simulation confirming prompt-injection and actor/role-confusion
resistance holds under repeated, varied runs rather than only on a handful of hand-picked
fixtures.

1.2. Key Words
performance test, latency budget, throughput, scenario scaling, guardrail load simulation,
statistical sampling.

1.3. Executive Summary
Performance tests validate that VoiceGate remains responsive across its supported scenario
catalog size and, distinctively for this project, that guardrail resistance (prompt
injection, actor/role confusion) holds across a large number of simulated gauntlet runs, not
merely the handful of fixtures exercised at the unit and integration tiers.

1.4. Key Findings
1.4.1. A single orchestration command (phase transition, transcription hand-off, scoring
invocation) must resolve within a documented latency budget (Section 1.7) at the default
scenario-catalog size.
1.4.2. A full simulated gauntlet run (mock/sandbox target agent, per 015_voicegate_
deployment.txt) must complete within a documented time budget, enabling large-sample
guardrail load-simulation runs.
1.4.3. Scenario-catalog scaling tests specifically measure whether performance degrades
acceptably (not catastrophically) as the persona/scenario catalog (`src/data/personas`,
`src/data/scenarios`) grows.
1.4.4. Guardrail load simulation is the mechanism by which prompt-injection and actor/
role-confusion resistance (008_voicegate_testing.txt Section 1.9) are empirically confirmed
to hold at scale, not merely on the specific fixtures used at the unit and integration tiers.
1.4.5. Persistence (save/restore of a gauntlet run) latency is measured separately from
in-run command latency, since it is dominated by serialization cost rather than engine
computation.

1.5. Philosophical Preamble
Performance testing here plays a second role beyond speed: it is the empirical check that
guardrail resistance is not an artifact of a small, hand-picked fixture set. A fast test
bench that only resists prompt injection on the three cases its own authors thought of is not
yet a trustworthy test bench; the large-sample simulation in Section 1.6.5 is how "resistant
on our fixtures" becomes "resistant at scale."

1.6. Performance Test Scope

1.6.1. Call-Orchestration Command Latency
Each orchestration command type is measured for resolution latency under the budgets in
Section 1.7.

1.6.2. Full-Gauntlet-Run Throughput
A full simulated gauntlet run against a mock/sandbox target agent completes within the budget
in Section 1.7, enabling repeated large-sample runs.

1.6.3. Scenario-Catalog Scaling
Command latency and full-run duration are measured at the default catalog size and at a
significantly larger synthetic catalog size, to confirm degradation remains proportional
rather than exponential.

1.6.4. Persistence Latency
Save and restore operations for a gauntlet run (015_voicegate_deployment.txt) are measured
independently against the budget in Section 1.7.

1.6.5. Guardrail Load Simulation
A large sample (minimum 1,000 simulated gauntlet runs, per Section 1.7) with randomly
generated prompt-injection payload variants and randomized speaker-channel-labeling
perturbations is run to produce: injection-resistance rate, role-confusion-resistance rate,
and false-Pass rate, empirically evaluating whether the guardrail behavior asserted at the
unit/integration tiers generalizes beyond the specific fixtures used there.

1.7. Performance Budgets
| Metric | Budget |
|--------|--------|
| Single orchestration command resolution | < 50 ms |
| Full simulated gauntlet run (default scenario catalog, mock target agent) | < 2 s |
| Save operation | < 200 ms |
| Restore operation | < 200 ms |
| Guardrail load-simulation sample size (minimum) | 1,000 runs |
| Guardrail load-simulation total wall-clock time (minimum sample) | < 10 minutes |
These are engineering targets for a hackathon-scale prototype, not sourced from an external
benchmark; declared here as ordinary engineering targets rather than a hallucination-envelope
invocation, since they describe non-content-affecting implementation performance rather than
statutory/policy content.

1.8. Tooling
1.8.1. `pytest-benchmark` (or equivalent) for command-latency and persistence-latency
measurement.
1.8.2. A dedicated, non-pytest simulation harness script for the large-sample guardrail load
simulation in Section 1.6.5, since 1,000+ run samples are not suited to the standard test
runner's per-test overhead.

1.13. Conclusion
Performance testing for VoiceGate serves the ordinary purpose of responsiveness validation
and the distinctive purpose of empirically confirming, at scale, that its mandatory guardrail
resistance is not merely a fixture-level artifact.
