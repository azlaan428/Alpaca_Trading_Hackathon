1.1. Abstract
This document specifies end-to-end (E2E) tests for VoiceGate: full user-facing flows across
the three UI screens under test — Test Bench, Call Review, and Risk Report — forming the top
tier of the testing pyramid established in 008_voicegate_testing.txt.

1.2. Key Words
end-to-end test, E2E, gauntlet run, Test Bench, Call Review, Risk Report, verdict badge,
rule citation, re-run diff.

1.3. Executive Summary
Where 011_voicegate_integration_tests.txt proves module-level cooperation, end-to-end tests
prove that a human operator, interacting only through the Test Bench, Call Review, and Risk
Report screens, can launch a gauntlet run against a mock/sandbox target agent, review the
resulting transcript and verdict, and — on a Fail — trigger a suggested-patch re-run and
confirm the fix, without a live production call ever being placed.

1.4. Key Findings
1.4.1. At least one full playthrough test exists per verdict outcome (Pass, Fail, Flag),
covering the full five-phase gauntlet (Greeting, Intent Discovery, Resolution Attempt,
Compliance Check, Wrap-up).
1.4.2. The Test Bench screen's persona/scenario selection and run-launch flow is exercised
explicitly, including launching against a mock/sandbox target agent only.
1.4.3. The Call Review screen's transcript display with inline findings and verdict badges
is exercised for at least one Pass and one Fail run.
1.4.4. The Risk Report screen's failed-call-vs-rule-text view and before/after re-run diff
are exercised as a dedicated scenario, distinct from the Call Review scenario.
1.4.5. The Fail-to-suggested-patch-to-re-run flow (patch proposed, never auto-applied,
operator confirms, re-run executes) is a dedicated E2E scenario spanning all three screens.
1.4.6. A guardrail scenario playthrough (prompt-injection payload and role-confusion
attempt embedded in a simulated call) is a dedicated E2E scenario confirming the verdict is
unaffected by the injected content, all the way through to the Risk Report display.

1.5. Philosophical Preamble
End-to-end tests are the closest a test suite comes to standing in the operator's seat. They
exist to answer one question the lower tiers cannot: does the finished experience, seen
through the actual Test Bench, Call Review, and Risk Report screens, deliver a trustworthy,
citation-backed verdict that an operator can act on with confidence
(001_voice_transcription_concept.txt Section 1.7)?

1.6. End-to-End Test Scope

1.6.1. Full-Screen-Flow Gauntlet Run
Test Bench (launch) -> live gauntlet run through all five phases -> Call Review (transcript
and verdict) -> Risk Report (if Fail/Flag), exercised once per verdict outcome (three
scenarios total).

1.6.2. Test Bench Persona/Scenario Selection and Launch
Selecting a persona/scenario catalog entry, confirming the run targets a mock/sandbox agent
only (never a live production endpoint, per 015_voicegate_deployment.txt), and launching the
run, with the live transcript rendering as the call proceeds.

1.6.3. Call Review Transcript and Verdict Display
The dual-channel transcript renders with inline findings and a verdict badge (Pass/Fail/
Flag); clicking a finding surfaces its supporting rule citation.

1.6.4. Risk Report Rule-Citation and Re-Run Diff
The Risk Report screen displays failed calls against the cited rule text, and a before/after
diff once a re-run has been executed following a suggested patch.

1.6.5. Fail-to-Patch-to-Re-Run Flow
A Fail verdict surfaces a suggested system-prompt patch (advisory only); the operator
explicitly confirms before any re-run is executed against the patched configuration; the
re-run's outcome is reflected in the Risk Report's before/after diff.

1.6.6. Guardrail Scenario Playthrough
A gauntlet run using a scenario fixture containing an embedded prompt-injection payload and a
speaker-role-confusion attempt is run end-to-end; the resulting verdict, transcript, and Risk
Report citation reflect the actual compliance content only, unaffected by the injected
instruction or attempted role swap.

1.7. Tooling
1.7.1. A browser/UI automation framework capable of driving the actual rendered Test Bench,
Call Review, and Risk Report screens (e.g. an in-repo Playwright-based harness), rather than
calling engine code directly, to genuinely exercise the UI layer.
1.7.2. E2E tests use the same seeded `rng_service` as lower tiers (009_voicegate_unit_
tests.txt Section 1.6.9) so gauntlet-run outcomes remain deterministic and repeatable, and
always target a mock/sandbox agent, never a live production endpoint.

1.10. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| E2E suite becoming slow/flaky as the top testing tier | Medium | Medium | Seeded `rng_service` (1.7.2) and a minimal scenario count (six groups) keep the suite bounded |
| A live production call being triggered accidentally during an E2E run | Low | High | 1.6.2/1.7.2 mandate mock/sandbox target agents only, enforced by 015_voicegate_deployment.txt |
| Guardrail scenario playthrough missed because it is folded into an ordinary Fail scenario | Low | Medium | 1.6.6 is a dedicated, separate scenario rather than folded into 1.6.1 |

1.12. Conclusion
Six end-to-end scenario groups give VoiceGate confidence that a real operator, using the
actual Test Bench, Call Review, and Risk Report screens against a mock/sandbox target agent,
can obtain and act on a trustworthy, citation-backed verdict, including under an active
guardrail-attack attempt.
