1.1. Abstract
This document defines the process for creating annotated market-scenario assets — individual
labeled market event instances used for regime model testing, stress scenario definition, and
educational scenario replay. It covers the asset creation lifecycle, labeling protocol,
storage convention, asset versioning, and quality-review checklist.

1.2. Key Words
scenario asset, market event, regime label, annotated scenario, stress test scenario, asset
lifecycle, labeling protocol, asset versioning, quality review.

1.3. Executive Summary
A scenario asset is a single annotated market event — a historical period or a synthetic
scenario defined by a set of bar sequences and associated regime labels, macro indicators, and
event metadata. Scenario assets are used to: (1) stress-test the operator pipeline against
specific extreme events; (2) evaluate MarketRegimeOperator precision/recall on known-regime
periods; (3) provide illustrative examples for documentation and testing. Assets are stored in
data/scenarios/ as JSON files with versioned metadata.

1.4. Key Findings
1.4.1. Regime-label consistency is mandatory: every bar in a scenario asset must have a
regime_id that matches the feature signatures in
alpaca_paper_trading_specifications_x_quant_x/025_xquantx_scenario_catalog.txt.
1.4.2. Scenario assets are the ground-truth input for MarketRegimeOperator evaluation; label
errors propagate directly into precision/recall metrics.
1.4.3. Synthetic assets must be generated using ScenarioGenerator with HMM emission
distributions from
alpaca_paper_trading_specifications_x_quant_x/027_xquantx_regime_archetypes.txt to ensure
statistical realism.
1.4.4. Every asset requires 2-person review before registration in manifest.json; the quality
review checklist (§1.9) is a release gate, not an optional review note.

1.5. Philosophical Preamble
A labeled scenario asset is only as credible as its annotation. An incorrectly labeled
historical period or a statistically implausible synthetic sequence undermines every
evaluation metric derived from it. Annotation discipline is the foundation of regime-model
validity.

1.6. Asset Types
1.6.1. Historical scenario asset: a slice of the historical dataset (per
030_xquantx_scenario_dataset_creation.txt) annotated with a confirmed ground-truth regime
label for the entire period. Example: "2020-03-16 to 2020-03-20 (COVID-19 sell-off),
regime=R04 bear-capitulation".
1.6.2. Synthetic stress scenario: a programmatically generated sequence of OHLCVBars
calibrated to produce a specific regime pattern (e.g. R07 macro-shock transition in 2 bars
followed by R04 bear-capitulation). Generated by ScenarioGenerator using the HMM emission
distributions from
alpaca_paper_trading_specifications_x_quant_x/027_xquantx_regime_archetypes.txt.
1.6.3. Regime-boundary scenario: a scenario spanning a known regime transition (e.g. R01
bull-quiet -> R07 macro-shock -> R04 bear-capitulation -> R01 recovery) used to test
MarketRegimeOperator's dwell-time and transition detection.

1.7. Asset Creation Lifecycle
1.7.1. Identify: source the scenario from historical market event databases (FRED, Bloomberg,
or Alpaca historical data) or define synthetic parameters.
1.7.2. Extract: pull the relevant OHLCVBar sequence from the historical dataset (for
historical assets) or generate via ScenarioGenerator (for synthetic assets).
1.7.3. Label: assign the ground-truth regime_id for each bar in the scenario using the
feature signatures in
alpaca_paper_trading_specifications_x_quant_x/025_xquantx_scenario_catalog.txt. Label is
human-reviewed.
1.7.4. Annotate: add event metadata (event_name, event_description, data_source,
scenario_type, ground_truth_regime_sequence, date_range).
1.7.5. Review: a second team member reviews the labels against the feature signatures.
Discrepancies are resolved by re-examining the feature values.
1.7.6. Version: assign asset_version semver string; save to
data/scenarios/{scenario_id}_v{version}.json.
1.7.7. Register: add asset to data/scenarios/manifest.json (asset_id, asset_version,
scenario_type, date_range, regime_sequence, created_date).

1.9. Quality Review Checklist
Before an asset is marked as review-complete:
1.9.1. All bars have valid OHLCVBar fields (high >= close >= low, prices > 0, volume >= 0).
1.9.2. ground_truth_regime_sequence covers every bar in date_range with no gaps.
1.9.3. Each regime_id in the sequence matches the feature signatures in
alpaca_paper_trading_specifications_x_quant_x/025_xquantx_scenario_catalog.txt.
1.9.4. event_description accurately describes the market event; data_source is cited.
1.9.5. Asset version is bumped if any field changes after initial publication.
1.9.6. Asset is registered in data/scenarios/manifest.json.

1.11. Storage and Naming Conventions
1.11.1. Storage path: data/scenarios/{scenario_id}_v{major}_{minor}_{patch}.json.
1.11.2. scenario_id format: {event-slug}-{YYYY-MM} (e.g. covid-selloff-2020-03).
1.11.3. All scenario IDs use lowercase kebab-case; no spaces or underscores in the event
slug.
1.11.4. Manifest file: data/scenarios/manifest.json; one entry per asset version.
1.11.5. Breaking label changes or date_range changes require a MAJOR version increment;
metadata-only changes require a MINOR increment; bar-value corrections require a PATCH
increment.

1.12. Asset Versioning Rules
1.12.1. Asset versions follow semver: MAJOR.MINOR.PATCH.
1.12.2. MAJOR increment: regime label changes or date_range changes (ground-truth altered).
1.12.3. MINOR increment: additional metadata fields (macro_snapshot, event_description
updates, symbol additions).
1.12.4. PATCH increment: minor data corrections (bar value corrections, typo fixes in
descriptive fields).
1.12.5. No field changes are permitted without a version bump; compliance is checked in
quality review §1.9.5.
1.12.6. Prior versions are retained in the data/scenarios/ directory and remain listed in
manifest.json with a deprecated flag for reproducibility of historical test runs.

1.13. Integration Workflow with Engineering
1.13.1. Asset files are placed in data/scenarios/ and listed in data/scenarios/manifest.json.
1.13.2. MarketRegimeOperator integration tests load scenarios from manifest.json to compute
precision/recall on known-regime periods.
1.13.3. StressTestRunner loads synthetic scenario assets from manifest.json to run operator
pipeline stress tests.
1.13.4. Asset loading failures cause test suite failure; no silent skips are permitted.
1.13.5. A pre-integration validation script checks manifest.json for completeness and all
asset JSON files for schema compliance before merge.

1.14. Extended Asset Constraints
1.14.1. Historical assets must include at minimum 5 trading days of bars.
1.14.2. Synthetic assets must document the HMM parameters used in generation in the asset's
JSON metadata (hmm_emission_params field).
1.14.3. Regime-boundary assets must span at least 2 distinct regime_ids in the
ground_truth_regime_sequence.
1.14.4. Assets with missing bars within date_range fail quality review §1.9.2 and may not
be registered in manifest.json.
1.14.5. Assets are immutable once registered; all corrections produce a new version per §1.12.

1.18. Conclusion
This document makes the scenario asset creation pipeline deterministic, auditable, and
directly connected to MarketRegimeOperator evaluation and operator pipeline stress testing.
Every labeled asset is a verifiable ground-truth instance traceable to feature signatures,
data sources, and review decisions.
