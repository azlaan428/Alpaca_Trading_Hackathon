1.1. Abstract
This document catalogs future platform extensions for X Quant X beyond the MVP scope. Each
extension is grounded in the existing architecture and specifies the minimal additional
components required. None of these extensions are implemented in the MVP sprint.

1.2. Key Words
future wishlist, live trading, options execution, reinforcement learning, LLM news pipeline,
mobile dashboard, multi-broker, regime learning, walk-forward optimization.

1.3. Executive Summary
The X Quant X MVP delivers paper trading, backtest, and a core Operator pipeline. Post-MVP
extensions fall into five tiers: (1) execution upgrades (live trading, options, multi-broker);
(2) intelligence upgrades (RL-based regime engine, streaming LLM news); (3) UI upgrades
(mobile dashboard, alert notifications); (4) research upgrades (walk-forward optimization,
synthetic data generation); (5) infrastructure upgrades (cloud deployment, distributed
backtesting).

1.4. Key Findings
1.4.1. Deferral is not deletion: every item here remains a candidate for a post-MVP roadmap
and must be re-evaluated against 001_xquantx_concept.txt Section 1.9.2 before being promoted
into an active specification document.
1.4.2. The largest deferred category is execution-facing capability (live trading, options
execution, multi-broker support) that the MVP intentionally replaces with paper trading via
the Alpaca paper endpoint per 016_xquantx_operating_modes.txt.
1.4.3. RL-based regime learning and streaming LLM news pipeline are the most complex deferred
items requiring new external dependencies and training infrastructure.
1.4.4. Any promotion of a wishlist item to active scope requires updating
001_xquantx_concept.txt Section 1.9.2 and the relevant Operator specification in the same
change, per 0000_documentation_standards.txt Section 1.6.7.

1.5. Philosophical Preamble
A wishlist is where ambition goes to wait its turn. Recording a deferred idea with its
rationale protects the vertical-slice-first design pillar (003_xquantx_philosophy.txt
Section 1.6.5) and the strict paper-trading-first constraint (001_xquantx_concept.txt
Section 1.9.2) without pretending the idea was never worth having.

1.6. Tier 1 — Execution Upgrades
1.6.1. Live trading mode: connect ExecutionOperator to the Alpaca live trading endpoint
(ALPACA_BASE_URL=https://api.alpaca.markets). Requires: risk audit sign-off, kill-switch
mechanism, emergency FLATTEN with manual override, regulatory compliance review.
1.6.2. Options execution: implement OptionsOperator using Alpaca Options API. Requires:
Black-Scholes and binomial pricing in the C++ kernel, Greeks computation (delta, gamma, vega),
options-specific risk rules (max vega exposure, max gamma exposure).
1.6.3. Multi-broker support: abstract ExecutionOperator behind a BrokerAdapter interface to
support additional brokers (Interactive Brokers via ib_insync, TD Ameritrade). Requires:
additional SDK submodules, per-broker order type mapping, unified fill event schema.
1.6.4. Fractional shares: if Alpaca supports fractional share trading, update
PortfolioOperator to use dollar-denominated allocation (not qty-denominated) for small
account sizes.

1.7. Tier 2 — Intelligence Upgrades
1.7.1. Reinforcement-learning regime engine: replace or augment the HMM/Bayesian
MarketRegimeOperator with a PPO or SAC agent trained on historical regime sequences. Requires:
OpenAI Gymnasium environment wrapper for the regime inference task, stable-baselines3
integration, walk-forward RL training loop.
1.7.2. Real-time streaming LLM news pipeline: replace the current batch news scoring with a
streaming NewsOperator that uses an LLM (GPT-4o or equivalent) to score incoming financial
news in real-time. Requires: news data subscription (Alpaca News API or Bloomberg API), LLM
API key, latency budget review (current offline batch: 5 min lag; streaming target: < 1 min
lag).
1.7.3. Learned signal weights: replace static regime-conditional signal weights w_i(r)
(currently in config/regimes.toml) with a learned weight vector updated via online gradient
descent after each bar. Requires: a bounded learning rate (to prevent catastrophic weight
drift), a learning curriculum (warm-start from static weights).
1.7.4. Cross-asset options strategy operators: VolatilityArbitrageOperator,
CalendarSpreadOperator, IronCondorOperator implementing volatility-surface-based strategies.

1.8. Tier 3 — UI Upgrades
1.8.1. Mobile dashboard: responsive Dash/React Native mobile app displaying the six panels
(P01–P06) with push notifications for FLATTEN and BLOCK verdicts.
1.8.2. Alert notification system: webhook integration (Slack, Discord, Telegram) for BLOCK and
FLATTEN events, with rule_id and measured_value in the notification payload.
1.8.3. Interactive strategy builder: a drag-and-drop Dash interface for composing Operator
DAGs without code, generating a TOML config representation.

1.9. Tier 4 — Research Upgrades
1.9.1. Walk-forward optimization: automated grid/Bayesian hyperparameter search over the
config/risk_rules.toml and config/regimes.toml parameters, with out-of-sample Sharpe as the
objective. Requires: Optuna or Ray Tune integration, parallel backtest execution.
1.9.2. Synthetic data generation: GAN-based or VAE-based synthetic OHLCV bar generator for
stress-testing the pipeline on extreme-regime scenarios not present in the historical dataset.
1.9.3. Multi-asset correlation factor model: replace the rolling 20-day pairwise correlation
with a dynamic factor model (Fama-French 3/5-factor or PCA-based) for the
CrossAssetSignalOperator.

1.10. Tier 5 — Infrastructure Upgrades
1.10.1. Cloud deployment: containerized deployment on AWS ECS or GCP Cloud Run. Requires:
secrets via AWS Secrets Manager / GCP Secret Manager, distributed logging to CloudWatch /
Google Cloud Logging, Terraform IaC for infrastructure provisioning.
1.10.2. Distributed backtesting: parallel backtest execution across multiple EC2/GCE
instances, each replaying a different historical window, with results aggregated centrally.
1.10.3. Real-time data subscription upgrade: from Alpaca IEX feed (free tier) to SIP feed
(full exchange coverage, paid tier) for higher signal quality.
