1.1. Abstract
This document defines the unit test contract for all Operator implementations in X Quant X
across all four languages (Python, Go, C++, Rust). It specifies: 100% branch coverage
requirement on all Operators, property-based testing for financial invariants, mock market
data stream patterns, and the test file naming and location conventions.

1.2. Key Words
unit tests, pytest, hypothesis, go test, Google Test, cargo test, 100% branch coverage,
property-based testing, operator contract test, mock market data, financial invariants,
temporal leakage test.

1.3. Executive Summary
Every Operator in X Quant X requires unit tests that achieve 100% branch coverage of the
Operator's process() method. Additionally, property-based tests must assert financial
invariants (signal bounds, probability sums, verdict coverage). Python unit tests use pytest
+ hypothesis. Go uses go test + rapid. C++ uses Google Test. Rust uses cargo test + proptest.
All unit tests are co-located in tests/{language}/operators/{operator_name}/ mirroring the
src/ tree.

1.4. Key Findings
1.4.1. 100% branch coverage is required on all Operator implementations in all four
languages. Any Operator that reaches merge with less than 100% branch coverage on its
process() method is a CI failure.
1.4.2. Every unit test file for an Operator must include: (a) a happy-path test with valid
inputs, (b) an invalid-input test verifying validate_inputs() returns errors without raising,
(c) at least one property-based test for the key financial invariant of that Operator type.
1.4.3. Market data is mocked: unit tests never call the Alpaca API. Python tests use pytest
fixtures with OHLCVBar factories. Go tests use mock WebSocket server. C++ tests use
in-memory test matrices. Rust tests use proptest strategies.
1.4.4. The temporal leakage invariant is tested as a unit-level property: for every
FeatureOperator, a property-based test asserts that feature(t) depends only on bars with
timestamp < t.
1.4.5. The operator_id() and schema_version() methods are tested for stability: same inputs
across multiple calls must produce identical outputs (idempotency).

1.5. Philosophical Preamble
A unit test is the smallest unit of trust the quantitative engine can offer: it isolates one
claim ("this Operator produces a signal within bounds," "this feature has no dependency on
future bars") and proves it independent of everything else. The required categories below
exist because each corresponds to one place where an untested behavior would silently produce
an incorrect signal, an unbounded weight, or a NaN Sharpe ratio — and any such silent failure
propagates directly into live capital allocation decisions. Financial correctness is not
verified at the integration tier alone; it is verified at the unit tier, Operator by Operator,
branch by branch, in all four languages.

1.6. Coverage Requirement

1.6.1. 100% Branch Coverage on Operator.process()
100% branch coverage is required on all Operator implementations in all four languages. Every
code branch inside process() — including all four RiskVerdict branches, all three portfolio
optimization branches, and all twelve regime probability assignment branches — must be
exercised by at least one unit test.

1.6.2. CI Enforcement
coverage.py (Python), go cover (Go), gcov/lcov (C++), and tarpaulin (Rust) produce
per-Operator branch coverage reports. Any Operator whose process() method falls below 100%
branch coverage is a CI failure and cannot be merged.

1.6.3. Exemptions
Test helper utilities and display-only code (dashboard/) are exempt from the 100% branch
requirement. All Operator classes are not exempt under any circumstances.

1.7. Property-Based Testing for Financial Invariants
For each Operator type, the following property-based tests are required:

1.7.1. DataOperator / NormalizationOperator
For any valid OHLCVBar, after normalization: high >= close >= low AND all prices > 0 AND
volume >= 0. Strategy: generate random valid OHLCVBars using
hypothesis.strategies.floats(min_value=0.01, max_value=10000.0).

1.7.2. FeatureOperator (All Subtypes)
For any sequence of bars in strictly ascending timestamp order, computed features have no
dependency on future bars (temporal leakage test). Assertion: replace bar(t+1) with an
adversarial value and verify that feature(t) is unchanged.

1.7.3. MarketRegimeOperator
For any valid feature vector, output regime_probabilities.values() sum to 1.0 +/- 1e-9 AND
confidence is in [0, 1]. Strategy: hypothesis.strategies.floats for feature values.

1.7.4. SignalOperator (All Subtypes)
For any valid (regime_state, feature_vector), output signal_score is in [-1, 1] AND
confidence is in (0, 1]. Strategy: generate diverse regime states and feature vectors.

1.7.5. RiskOperator
For any valid (signal_score, portfolio_snapshot, regime_state), output verdict is one of
{ALLOW, REDUCE, BLOCK, FLATTEN}. All four verdict branches must be reachable and tested by
at least one explicit test case.

1.7.6. PortfolioOperator
For any valid (signal, risk_verdict=ALLOW), output AllocationVector weights sum to <= 1.0
AND each weight is in [-1, 1]. No NaN or Inf weights are permitted.

1.7.7. PerformanceOperator
For any non-empty fill history, Sharpe = mean(returns) / std(returns) * sqrt(252) with no
division by zero (returns std = 0 => Sharpe = 0.0, not NaN).

1.8. Mock Market Data Patterns

1.8.1. Python
pytest fixture `sample_ohlcv_bars(n=60)` generates n valid OHLCVBars with timestamps
strictly increasing by 1 minute. `sample_regime_state(regime_id="R01")` generates a valid
RegimeState for R01. No call to the Alpaca API is permitted in any unit test.

1.8.2. Go
Mock WebSocket server using httptest.NewServer + net/http/httptest. Sends pre-generated
OHLCVBar JSON events on connection. The mock server is created per test and torn down in
t.Cleanup().

1.8.3. C++
In-memory test matrices (Eigen::MatrixXd) with known values for Kalman filter update step
tests. Expected output is computed analytically for validation. No file I/O in unit tests.

1.8.4. Rust
proptest strategies generating valid OhlcvBar structs with field invariants enforced by the
strategy generator. The strategy ensures open, high, low, close ordering constraints before
any test assertion runs.

1.9. Test File Naming and Location

1.9.1. Python
tests/python/operators/{layer}/{operator_name}/test_{operator_name}.py
Example:
tests/python/operators/signal/momentum/test_momentum_signal_operator.py

1.9.2. Go
Co-located with the source file per Go convention:
src/go/internal/stream/stream_handler_test.go

1.9.3. C++
tests/cpp/kernel/test_kalman_filter.cpp
tests/cpp/kernel/test_covariance.cpp
(mirrors src/cpp/src/ tree)

1.9.4. Rust
Inline tests in the source file (`#[cfg(test)] mod tests { ... }`) plus integration tests in
the tests/ directory at the crate root.

1.10. Example Unit Test (Python, MomentumSignalOperator)
The following example demonstrates the required happy-path, invalid-input, and
property-based test pattern for a SignalOperator:

    # tests/python/operators/signal/momentum/test_momentum_signal_operator.py
    import pytest
    from hypothesis import given, strategies as st
    from xquantx.operators.signal.momentum import MomentumSignalOperator
    from xquantx.schemas import RegimeState, OHLCVBar

    @pytest.fixture
    def operator():
        return MomentumSignalOperator(operator_id="test-momentum-v1")

    def test_process_happy_path(operator, sample_ohlcv_bars, sample_regime_state):
        result = operator.process({"bars": sample_ohlcv_bars, "regime": sample_regime_state})
        assert -1.0 <= result.signal_score <= 1.0
        assert 0.0 < result.confidence <= 1.0

    def test_validate_inputs_missing_bars(operator, sample_regime_state):
        result = operator.validate_inputs({"bars": [], "regime": sample_regime_state})
        assert len(result.errors) > 0

    @given(
        signal_score=st.floats(min_value=-2.0, max_value=2.0, allow_nan=False)
    )
    def test_signal_score_bounds(operator, sample_ohlcv_bars, sample_regime_state,
                                  signal_score):
        # Property: regardless of raw score, output must be clamped to [-1, 1]
        result = operator.process({"bars": sample_ohlcv_bars, "regime": sample_regime_state})
        assert -1.0 <= result.signal_score <= 1.0

1.13. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Property test strategy generates inputs that avoid an untested branch | Medium | High | Supplement property tests with explicit edge-case tests for each known branch |
| 100% coverage achieved by trivial tests that do not assert correctness | Medium | High | Code review: every test must have at least one assert on the output value, not just on absence of exception |
| Go/C++/Rust tests not run in CI | Medium | High | §1.7 of 008_xquantx_testing.txt: all four language runners are mandatory CI steps |
