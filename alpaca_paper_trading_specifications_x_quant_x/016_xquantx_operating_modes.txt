1.1. Abstract
This document defines the four operating modes of X Quant X — Paper, Backtest, Dry-run,
and Live-shadow — specifying per-mode data sources, fill sources, execution constraints,
configuration flags, and mode-specific logging behavior. The MVP delivers Paper and Backtest
modes only; Dry-run and Live-shadow are architecturally specified but not implemented in the
MVP sprint.

1.2. Key Words
operating mode, paper trading, backtest, dry-run, live-shadow, Alpaca API, historical
replay, simulated fills, mode flag, SessionContext, mode-conditional logging.

1.3. Executive Summary
X Quant X operates in one of four named modes: Paper (live Alpaca stream + real
paper-trading fills), Backtest (historical OHLCV replay + simulated fills), Dry-run (live
Alpaca stream + simulated fills, no orders submitted), and Live-shadow (live stream + paper
fills + parallel live-trading comparison). All Operators receive the current mode via
SessionContext. The mode determines which DataOperator adapter is active, whether
ExecutionOperator submits real orders or logs simulated fills, and which performance metrics
are meaningful (live fill prices vs VWAP estimate).

1.4. Key Findings
1.4.1. Paper mode is the MVP primary mode: live Alpaca WebSocket stream, real Alpaca
paper-trading API fills, real-time P&L and position tracking.
1.4.2. Backtest mode replays historical OHLCV bars from file/DB with clock-controlled
deterministic progression, VWAP-estimate simulated fills, and no external API calls.
1.4.3. Dry-run mode uses the live Alpaca stream but logs simulated fills without submitting
any order; useful for live strategy validation before committing to paper fills.
1.4.4. Live-shadow mode (future scope only) runs Paper fills and a real live account in
parallel, comparing performance.
1.4.5. The active mode is set once per session via SessionContext.mode (str: "paper" |
"backtest" | "dry_run" | "live_shadow") and is immutable for the lifetime of the session.
1.4.6. CI must include a Backtest mode regression run on the test historical dataset as a
mandatory gate; Paper mode integration tests use the Alpaca sandbox environment.

1.5. Philosophical Preamble
A trading platform that cannot run in a controlled, deterministic backtest mode provides no
honest way to evaluate strategy correctness before real capital (even paper capital) is at
risk. The operating mode is therefore not a cosmetic setting; it is the architectural
partition between "we are running safe replay" and "we are sending orders to an API." Every
code path that would behave differently in Paper vs Backtest must branch explicitly on
SessionContext.mode — never implicitly on environment variables or undocumented startup
flags.

1.6. Mode Definitions

1.6.1. Paper Mode (MVP, primary)
Data source: Live Alpaca WebSocket stream (market data) + Alpaca REST API (account,
positions). Fill source: Alpaca paper-trading API real fills (paper account, not real money).
Order submission: ExecutionOperator calls alpaca.submit_order() on the paper endpoint.
SessionContext.mode = "paper". Logging: all orders, fills, regime transitions, and signal
emissions logged to AUDIT_LOGS/. P&L: real-time unrealized and realized P&L from Alpaca
account state. Performance metrics: computed from real fill prices.

1.6.2. Backtest Mode (MVP, optional)
Data source: Historical OHLCV bars from Parquet/CSV file or SQLite DB. Fill source:
Simulated fills using VWAP estimate from the same bar (or next-bar open if market order
simulation requires it). Order submission: No external API calls; fills logged locally with
simulated fill_price. SessionContext.mode = "backtest". Clock: Synthetic clock advanced one
bar at a time; strictly monotonically increasing timestamps enforced. Temporal leakage check:
DataOperator asserts strictly_increasing_timestamps on every bar before emitting to the
pipeline. Logging: all orders, fills, and performance metrics logged to AUDIT_LOGS/ for
post-hoc analysis. P&L: computed from simulated fill prices; clearly labeled as backtest
results, not live performance.

1.6.3. Dry-run Mode (future scope, not MVP)
Data source: Live Alpaca WebSocket stream (identical to Paper). Fill source: Simulated fills
logged locally; no order submitted to any API. Order submission: None (ExecutionOperator
logs the order intent and simulated fill, does not call alpaca.submit_order()).
SessionContext.mode = "dry_run". Use case: Live strategy validation and latency measurement
without any order risk.

1.6.4. Live-shadow Mode (future scope, not MVP)
Data source: Live Alpaca WebSocket stream. Fill source: Paper fills + optional real live
account fills for comparison. SessionContext.mode = "live_shadow". Use case: Parallel
comparison of paper strategy vs live execution; not implemented in MVP.

1.7. Mode Configuration
Mode is set at session startup via config/paper_trading.toml or config/backtest.toml. The
mode flag is read once, stored in SessionContext, and never changed mid-session.
Mode-conditional code must always use explicit if/elif branches on the SessionContext.mode
string; no implicit mode detection via environment variables or undocumented startup flags.

1.8. Mode-Specific Logging
In Paper mode: all order events, fill events, regime transitions, signal emissions, and
risk-gate verdicts are logged to AUDIT_LOGS/ as NDJSON with the mode field set to "paper".
In Backtest mode: same log schema, mode field set to "backtest". Log entries include the
synthetic clock timestamp as both simulation_ts and wall_ts for provenance.

1.9. Deferred Modes
Dry-run mode and Live-shadow mode are architecturally specified in Sections 1.6.3 and 1.6.4
but are not implemented in the MVP sprint. They are tracked in
alpaca_paper_trading_specifications_x_quant_x/018_xquantx_future_wishlist.txt. No code path
targeting these modes is required for the MVP CI gate.

1.10. Mode Isolation Invariants
SessionContext.mode is set once at session startup and is immutable for the lifetime of the
session. Any write attempt after initialization raises AttributeError. All mode-conditional
code must branch explicitly using if/elif on the SessionContext.mode string value ("paper",
"backtest", "dry_run", "live_shadow"); no implicit mode detection via environment variables
or undocumented flags is permitted.

1.13. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Code path behaves differently in paper vs backtest without explicit mode branch | Medium | High | CI backtest regression run must produce identical results for fixed seeds; any mode-conditional behavior must be in a named function |
| Temporal leakage in backtest (future bar data used in current bar decision) | Medium | Critical | §1.6.2 DataOperator asserts strictly_increasing_timestamps; validated by unit test per 019_xquantx_data_structures_algorithms.txt §1.4.6 |
| Paper mode accidentally connecting to live endpoint | Low | Critical | Alpaca SDK configured with ALPACA_BASE_URL=https://paper-api.alpaca.markets; CI validates URL in integration test |
| Mode changed mid-session | Low | High | SessionContext.mode is a read-only field after initialization; any write attempt raises AttributeError |

1.15. Conclusion
The four operating modes provide a clear architectural partition between controlled replay
(Backtest), safe live validation (Dry-run), paper-trading (Paper), and future live-shadow
comparison. MVP delivers Paper and Backtest only; all mode-conditional code branches
explicitly on SessionContext.mode.
