1.1. Abstract
This document defines the multi-language repository scaffold for X Quant X — a Python/Go/
C++/Rust quantitative paper-trading platform built on the Alpaca API. It establishes
directory layout, language-layer boundaries, package responsibilities, and module isolation
rules that all implementation files must follow.

1.2. Key Words
scaffolding, repository layout, module boundaries, language layers, operator hierarchy,
Python, Go, C++, Rust, Alpaca SDK, src layout, tests, schemas, config, data.

1.3. Executive Summary
The repository is organized into four language source trees (src/python/, src/go/, src/cpp/,
src/rust/) plus shared cross-language artifacts (schemas/, config/, data/). Each language
tree is independently buildable. Alpaca SDK submodules live in tools/alpaca/. Tests mirror
the source tree. The Python layer hosts Operators, Agents, ML models, and Alpaca API calls.
The Go layer hosts streaming data ingestion, WebSocket handling, and low-latency API
services. The C++ layer hosts numerical kernels (Kalman filter, covariance, options pricing).
The Rust layer hosts concurrent data-pipeline components and Parquet/Arrow serialization.

1.4. Key Findings
1.4.1. The scaffold directly extends the prior game-project and xquantx module isolation
plan into a four-language monorepo layout.
1.4.2. Language boundaries are hard: Python does not re-implement C++ kernel logic; Go does
not maintain regime state (Python does); C++ does not call Alpaca API (Python does).
1.4.3. The shared `schemas/` directory holds all language-neutral schema definitions
(Protocol Buffers or JSON Schema) — the single source of truth for OHLCVBar, Order,
Position, RegimeState, and all other cross-language data structures.
1.4.4. `tests/` mirrors every source sub-tree one-to-one (tests/python/, tests/go/,
tests/cpp/, tests/rust/).
1.4.5. `tools/alpaca/` contains all Alpaca SDK submodules (alpaca-py, alpaca-trade-api-go,
alpaca-mcp-server, alpaca-skills, cli).

1.5. Philosophical Preamble
Scaffolding is the skeleton that keeps a rapidly built quantitative platform from collapsing
under its own ambition. A directory layout is itself a claim about responsibility boundaries;
getting it right before implementation begins is cheaper than untangling coupled Python ML
code and Go streaming code under a deadline. For a four-language quantitative system, clean
language-layer boundaries are what keeps the Kalman filter kernel from being silently
reimplemented in three different languages with three subtly different numerical conventions.

1.7. Module Responsibilities
| Layer | Language | Responsibility | Must Never |
|-------|---------|---------------|-----------|
| operators/ | Python | Typed Operator implementations | Import from dashboard/ or api/ |
| agents/ | Python | Agent compositions of Operators | Bypass RiskOperator in the pipeline |
| dashboard/ | Python | Plotly/Dash visualization | Contain trading logic or Operator implementations |
| cmd/ | Go | Entry points for streaming/API services | Maintain regime state (Python does) |
| internal/stream/ | Go | Alpaca WebSocket live data ingestion | Call Alpaca paper-trade order API (Python does) |
| include/ + src/ | C++ | Pure numerical kernels | Call any external API or read from disk |
| src/pipeline/ | Rust | Concurrent data pipeline orchestration | Hold regime state or make trading decisions |
| schemas/ | Language-neutral | Single source of truth for all data types | Contain executable logic |
| config/ | Language-neutral | Declarative configuration only | Contain executable logic (thresholds only) |

1.8. Scaffolding Rules
1.8.1. Language boundaries are hard: no Python file re-implements a function that already
exists in the C++ numerical kernel. No Go file maintains regime state. No C++ file calls any
external API.
1.8.2. Every Operator in Python implements exactly the four interface methods: `process()`,
`validate_inputs()`, `schema_version()`, `operator_id()`.
1.8.3. All cross-language data types are defined in `schemas/` first. No language defines its
own canonical data structure if it crosses a language boundary.
1.8.4. `config/` contains only declarative TOML/YAML: threshold values, regime priors, risk
limits. No executable logic in configuration files.
1.8.5. `data/` historical datasets are gitignored; only schema and scenario definitions are
versioned.
1.8.6. Every new Operator gets a corresponding unit test in `tests/python/operators/` before
any integration test is written.

1.11. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Python re-implementing C++ kernel functions | Medium | High | §1.8.1 language boundary rule enforced in code review and CI |
| schemas/ diverging across language implementations | Medium | High | schemas/ is single source of truth; CI validates all language bindings against it |
| config/ accumulating executable logic | High | Medium | §1.8.4 rule: config/ review checklist; CI lint for executable constructs in TOML |
| Missing test for a new Operator | High | Medium | §1.8.6 rule: test-first; CI coverage gate requires 100% branch on all Operators |

1.13. Conclusion
The four-language scaffold establishes clear responsibility boundaries before implementation
begins. Every implementation file must reside in the correct language sub-tree and respect
the language boundary rules in §1.8.
