1.1. Abstract
This document defines the package/module scaffolding for the VoiceGate Python backend,
adapting the module isolation plan first sketched for the prior DarkStrategy_XParadoxX game
project into a concrete directory layout for this repository (X_Voice_X), now repurposed as
an automated compliance/red-team test bench for voice AI agents.

1.2. Key Words
scaffolding, package layout, module boundaries, orchestration, services, tests, py.typed,
repository structure.

1.3. Executive Summary
The backend is organized into four top-level packages — `voicegate` (call orchestration,
persona/scenario engines, transcription, compliance scoring, verdicts, patch advice, event
log, RNG), `data` (static personas/scenarios/statutory rules/company-terms snapshots),
`services` (patch-adviser client, persistence for run history/re-runs), and `api` (command/
contract surface for the frontend) — plus `tests` mirroring every package, so that the
verdict-producing engines remain fully decoupled from any presentation layer.

1.4. Key Findings
1.4.1. The scaffolding directly reuses and extends the module isolation plan carried forward
from the prior game-project ideation, adapted from a five-package game layout to the
four-package VoiceGate layout below.
1.4.2. `voicegate/` contains only the orchestration and decision-making engines (call
orchestration, persona/scenario simulation, transcription, compliance scoring, verdicts,
patch advice); it must never import from a presentation or API layer.
1.4.3. `services/patch_adviser` must only read a serialized transcript/verdict summary and
return a suggested (advisory-only) system-prompt patch; it must never auto-apply a patch
without human confirmation, and it must never hold a reference to live mutable call state.
1.4.4. `tests/` mirrors every top-level package one-to-one.
1.4.5. Every package and sub-package contains an `__init__.py`; the repository root carries
`py.typed` to advertise inline type information to consumers, per
005_voicegate_coding_standards.txt Section 1.9.3.

1.5. Philosophical Preamble
Scaffolding is the skeleton that keeps a rapidly generated hackathon prototype from collapsing
under its own ambition. A directory layout is itself a claim about responsibility boundaries;
getting it right before implementation begins is cheaper than untangling coupled
orchestration-and-UI code under a deadline — and for a compliance test bench specifically, a
clean boundary between the scoring/verdict engines and any external service is what keeps a
Pass/Fail/Flag verdict auditable rather than merely plausible.

1.6. Repository Layout
```
X_Voice_X/
    voice_processing_specifications/   # this specification corpus
    src/
        voicegate/
            call_orchestrator.py   # call lifecycle sequencing (Greeting/Intent Discovery/
                                    # Resolution Attempt/Compliance Check/Wrap-up)
            persona_engine.py      # persona archetype behavior (patience, escalation rate,
                                    # deception likelihood, vulnerability flag)
            scenario_engine.py     # scenario/category x intensity-tier selection and
                                    # variance injection
            transcription_engine.py# both-sides call transcription; treats transcript
                                    # content as untrusted DATA, never instructions
            compliance_scoring_engine.py# scores transcript vs statutory rules and company
                                    # terms snapshots
            verdict_engine.py      # Pass/Fail/Flag verdict with rule citation
            patch_adviser.py       # advisory-only suggested system-prompt patch
            event_log.py          # structured, human-readable event records
            rng_service.py        # seeded random-number service for reproducible runs
        data/
            personas.py           # persona archetype definitions and stat-blocks
            scenarios.py          # scenario/persona catalog (category x intensity)
            statutory_rules.py    # structured statutory rule citations (rule IDs only, never
                                   # full statute text reproduced)
            company_terms_snapshots.py # scraped/published company T&C snapshots per run
        services/
            patch_adviser_client.py # client wrapper for the advisory patch service
            persistence.py         # run-history persistence and re-run retrieval
        api/
            commands.py           # START_RUN, SELECT_PERSONA, SELECT_SCENARIO,
                                   # SUBMIT_VERDICT_REVIEW, REQUEST_PATCH, CONFIRM_PATCH,
                                   # RE_RUN_GAUNTLET command schema for the frontend to invoke
    tests/
        voicegate/
        data/
        services/
        api/
```

1.7. Module Responsibilities
| Package | Responsibility | Must Never |
|---------|------------------|------------|
| `src/voicegate` | Call orchestration, persona/scenario simulation, transcription, scoring, verdicts, patch advice | Import from `api` or any presentation layer |
| `src/data` | Static, versioned personas/scenarios/statutory-rule/company-terms data | Contain executable orchestration or scoring logic |
| `src/services` | Patch-adviser client, persistence | Mutate call state directly, or auto-apply a patch without human confirmation |
| `src/api` | Command schema/contract for the frontend | Contain orchestration or scoring logic itself |
| `tests` | Mirror of all packages above | Depend on production data changing test outcomes without a seeded RNG |

1.8. Scaffolding Rules
1.8.1. No package may exceed a single clearly named responsibility (see
005_voicegate_coding_standards.txt Section 1.7.4).
1.8.2. Every new module requires a corresponding test module in `tests/` before it is
considered complete.
1.8.3. Cross-package imports flow one direction only: `data` -> `voicegate` -> `services`/
`api`; reverse imports are disallowed to prevent circular dependencies (see
023_voicegate_modules_imports.txt).

1.11. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Orchestration/scoring logic leaking into `api` or `services` under time pressure | Medium | High | 1.8.3 import direction rule enforced via lint/import-graph check in CI |
| Missing `__init__.py` or `py.typed` breaking type distribution | Low | Medium | Scaffolding checklist item in code review |
| Test package drifting out of sync with production package structure | Medium | Medium | 1.8.2 mandates a test module per new production module |
| `patch_adviser` auto-applying a patch without human confirmation | Low | High | 1.4.3 and the `services` "must never" column enforced via code review and an explicit human-confirmation gate in `api/commands.py` (`CONFIRM_PATCH`) |

1.13. Conclusion
The scaffolding isolates the deterministic-where-possible orchestration/scoring engines from
data, services, and the API/frontend contract, directly fulfilling the architecture principle
carried forward from the original ideation session and adapted to VoiceGate's compliance-
testing domain.
