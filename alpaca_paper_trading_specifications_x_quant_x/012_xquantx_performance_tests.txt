1.1. Abstract
This document defines the performance test budgets and measurement procedures for X Quant X,
covering: order submission latency (paper API), market data ingestion throughput (backtest
replay), per-operator execution time budget (paper mode), memory ceiling per session, and
profiling tooling per language.

1.2. Key Words
performance tests, latency, throughput, P99, order submission, market data ingestion,
backtest replay, per-operator time budget, memory ceiling, profiling, pytest-benchmark,
pprof, perf, cargo bench.

1.3. Executive Summary
X Quant X performance tests enforce four budgets: (1) order submission latency ≤ 200ms P99
in paper mode; (2) market data ingestion throughput ≥ 1,000 daily bars/second in backtest
replay; (3) per-operator execution time ≤ 50ms P99 in paper mode; (4) memory ceiling ≤ 2GB
RSS per session for the Python process. Performance tests run in a separate CI step after
all functional tests are green.

1.4. Key Findings
1.4.1. Order submission latency: measured from AlpacaPaperExecutionOperator.process() call
to receipt of Alpaca API HTTP response. Budget: ≤ 200ms P99 over 100 submissions. Measured
in Dry-run mode against the Alpaca paper endpoint.
1.4.2. Backtest replay throughput: measured as bars/second through the full operator
pipeline (DataOperator → ValidationOperator). Budget: ≥ 1,000 daily bars/second. Measured
on the historical test dataset.
1.4.3. Per-operator execution time: measured as the wall-clock time for each
Operator.process() call in isolation. Budget: ≤ 50ms P99. Critical path operators
(MarketRegimeOperator, SignalAggregationOperator) are measured individually.
1.4.4. Memory ceiling: measured as peak RSS of the Python process during a 1-hour
paper-mode session. Budget: ≤ 2GB. Go service and C++ kernel have separate budgets
(≤ 512MB each).
1.4.5. Profiling tooling: Python uses py-spy (sampling profiler) and memory_profiler. Go
uses pprof. C++ uses perf/valgrind. Rust uses cargo bench + criterion.

1.6. Order Submission Latency Budget
1.6.1. Budget: ≤ 200ms P99 (99th percentile) latency from
AlpacaPaperExecutionOperator.process() call to receipt of Alpaca API response with order_id.
1.6.2. Measurement: Dry-run 100 consecutive market-order submissions (symbol: SPY, qty: 1).
Record wall-clock time for each. Compute P50, P95, P99.
1.6.3. Tooling: pytest-benchmark in Python. Measure with time.perf_counter() around the
Alpaca client call.
1.6.4. CI enforcement: performance test step emits a structured log with P99 value. CI
fails if P99 > 200ms.
1.6.5. Note: this budget is network-dependent and may vary; the test is run in Dry-run mode
against the Alpaca sandbox. Sandbox P99 latency > 200ms is reported as a WARNING (not CI
failure) if clearly attributable to sandbox network conditions; repeated failures require
investigation.

1.7. Backtest Replay Throughput Budget
1.7.1. Budget: ≥ 1,000 daily bars/second through the full operator pipeline (DataOperator
→ FeatureOperator → MarketRegimeOperator → SignalOperator → RiskOperator →
PortfolioOperator → PerformanceOperator).
1.7.2. Measurement: replay 2,520 daily bars (10 trading years) for a single symbol and
measure total wall-clock time. Target: ≤ 2.52 seconds (= 2,520 bars / 1,000 bars/sec).
1.7.3. Tooling: pytest-benchmark. Time the full BacktestSession.run() call.
1.7.4. CI enforcement: CI fails if throughput < 1,000 bars/second over the reference
dataset.

1.8. Per-Operator Execution Time Budget
1.8.1. Budget: ≤ 50ms P99 per Operator.process() call in paper mode (single-symbol,
real-time bar).
1.8.2. Critical-path operators (tested individually): MarketRegimeOperator,
SignalAggregationOperator, RiskOperator, PortfolioOperator.
1.8.3. Measurement: 1,000 calls per operator with a valid cached feature vector. Record
wall-clock time per call.
1.8.4. Tooling: pytest-benchmark for Python; go test -bench for Go; Google Benchmark for
C++; criterion for Rust.
1.8.5. Expected P99 per operator: MarketRegimeOperator ≤ 50ms (Kalman + Bayesian step),
SignalAggregationOperator ≤ 10ms, RiskOperator ≤ 5ms, PortfolioOperator ≤ 50ms
(mean-variance optimization, ≤ 20 assets).

1.9. Memory Ceiling
1.9.1. Python process RSS budget: ≤ 2GB during a 1-hour paper-mode session with 5 symbols.
1.9.2. Go streaming service RSS budget: ≤ 512MB during a 1-hour live-stream session.
1.9.3. C++ kernel RSS budget: ≤ 512MB during any session (Kalman state matrices for ≤ 12
regimes × 12 state dimensions).
1.9.4. Tooling: memory_profiler (Python), pprof heap (Go), valgrind massif (C++).
1.9.5. Measurement: a 1-hour paper-mode simulation with 5 symbols tracks peak RSS every 60
seconds. CI fails if peak RSS > 2GB at any point.

1.13. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
