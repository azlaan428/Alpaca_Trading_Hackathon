1.1. Abstract
This document is the authoritative naming-convention specification for the X Quant X
quantitative paper-trading platform, covering all four implementation languages: Python,
Go, C++, and Rust. It defines identifier case styles, suffix conventions, domain-specific
vocabulary, and cross-language consistency rules that ensure operator type names, schema
field names, and verdict values are unambiguous across the entire platform DAG.

1.2. Key Words
naming convention, snake_case, PascalCase, SCREAMING_SNAKE_CASE, camelCase, kebab-case,
Operator suffix, Agent suffix, RiskVerdict, cross-language consistency, schema field
alignment, trading domain vocabulary, X Quant X, multi-language platform.

1.3. Executive Summary
X Quant X follows language-idiomatic naming conventions in each of its four implementation
languages while enforcing a cross-language consistency layer for canonical schema field names,
regime identifiers, operator type names, and verdict values. Python uses snake_case for
functions and variables and PascalCase for classes, with mandatory Operator and Agent suffixes.
Go uses exported CamelCase and unexported camelCase. C++ uses PascalCase for types and
snake_case for functions and members, with fully qualified namespace prefixes in headers. Rust
uses snake_case for functions and variables and PascalCase for types, with kebab-case crate
names. All four languages agree on canonical field names, verdict values, and operator type
identifiers at schema boundaries.

1.4. Key Findings
1.4.1. All Operator subclasses in Python end in the suffix Operator
(e.g. MomentumSignalOperator, AlpacaPaperExecutionOperator); this suffix is never omitted or
abbreviated. All Agent classes end in the suffix Agent (e.g. EarthPortfolioAgent,
AirHedgeAgent).
1.4.2. The RiskVerdict enum values are ALLOW, REDUCE, BLOCK, FLATTEN across all four
languages. These values are never aliased, shortened, or renamed in any language binding.
1.4.3. Canonical schema field names are defined in snake_case and must be identical in Python
and Rust. Go exported field names use the CamelCase equivalent. C++ private member variables
append a trailing underscore to the snake_case name.
1.4.4. Regime identifiers R01 through R12 (defined in 025_xquantx_scenario_catalog.txt) are
the canonical string keys for all regime lookups; no language-specific substitution
(e.g. integer keys or enum ordinals as primary identifiers) is permitted at schema boundaries.
1.4.5. Trading domain vocabulary is standardized: equity (not stock), position_weight (not
allocation), regime_id (not state_id), signal_score (not prediction), fill_price (not
execution_price). These terms apply to Python and Rust snake_case fields and to the
CamelCase equivalents in Go and PascalCase aliases in C++.
1.4.6. File names follow snake_case in Python, Go, C++, and Rust; crate names use kebab-case
in Cargo.toml. Spec files follow the NNN_xquantx_description.txt corpus convention.

1.5. Philosophical Preamble
A name is the first and cheapest documentation a reader encounters. In a multi-language
platform where a data type crosses from a Rust serializer to a Python operator to a Go stream
handler, a name that means different things in different layers is a latent defect waiting to
become a runtime mismatch. The cross-language consistency rules in Section 1.10 exist to make
that class of defect visible at code-review time rather than at production time.

The Operator and Agent suffix rules in Section 1.6 exist for the same reason: when every
executable unit of computation ends in Operator and every domain composition ends in Agent,
a reader can determine the abstraction layer of any class from its name alone, without
consulting the import tree. That legibility compounds across thousands of lines of code in
four languages.

1.6. Python Naming Conventions
1.6.1. Functions and variables: snake_case (e.g. compute_signal_score, regime_state,
position_weight, fill_price). Names are descriptive nouns for variables and verb phrases for
functions; single-letter names are prohibited outside tightly scoped, obviously bounded loops.
1.6.2. Classes: PascalCase (e.g. MomentumSignalOperator, KalmanRegimeOperator,
EarthPortfolioAgent, MeanVariancePortfolioOperator). Class names describe the concept
represented; implementation detail words (Manager, Data, Handler) are used only where they
add real meaning.
1.6.3. Operator suffix: all Operator subclasses end in Operator without exception
(e.g. MeanReversionSignalOperator, AlpacaPaperExecutionOperator, NormalizationOperator,
BollingerOperator). Abbreviating or dropping the suffix is a naming violation.
1.6.4. Agent suffix: all Agent classes end in Agent (e.g. EarthPortfolioAgent, AirHedgeAgent,
FireVolatilityAgent, WaterMacroAgent). Agent classes compose operators into DAGs; they are
not operators themselves and must not carry the Operator suffix.
1.6.5. Constants: SCREAMING_SNAKE_CASE declared in config.py or constants.py at the package
level (e.g. MAX_DRAWDOWN_PCT = 0.15, KELLY_FRACTION_CAP = 0.25, MIN_REGIME_DWELL_BARS = 5,
DEFAULT_LOOKBACK_BARS = 60). Inline magic numbers and hardcoded string literals are
prohibited throughout the operator and agent layers.
1.6.6. Private members: single leading underscore for module-internal or class-internal
identifiers not part of the public API (e.g. _kalman_state, _apply_signal_decay,
_regime_cache). Double underscores are reserved for Python name-mangling; they are not used
as a general private convention.
1.6.7. Files: snake_case.py (e.g. momentum_signal_operator.py, kalman_regime_operator.py,
mean_variance_portfolio_operator.py, alpaca_paper_execution_operator.py).
1.6.8. Trading domain vocabulary: equity (not stock); position_weight (not allocation);
regime_id (not state_id); signal_score (not prediction); fill_price (not execution_price);
avg_entry_price (not cost_basis); portfolio_snapshot (not account_snapshot).

1.7. Go Naming Conventions
1.7.1. Exported types and functions: CamelCase (e.g. StreamHandler, OrderSubmitter, OHLCVBar,
RegimeState, AlpacaClient). Exported names are the package public API and must be clear and
self-documenting without consulting the package documentation.
1.7.2. Unexported types and functions: camelCase (e.g. reconnect, parseBar, retrySubmit,
computeBackoff). Unexported names are package-internal; they follow Go idiom for unexported
identifiers.
1.7.3. Package names: lowercase, single word, no underscores (stream, order, schema,
internal). Package names are the first part of the qualified name that callers see; brevity
and clarity take precedence over mirroring the Python subpackage path structure.
1.7.4. Operator interface: interface names end in Operator in Go type definitions
(e.g. DataOperator, StreamOperator). Interface method sets align with the Python Operator
base class contract for cross-language clarity.
1.7.5. Constants: CamelCase for exported constants (MaxRetries, DefaultLookbackBars); all-caps
acceptable for well-known financial abbreviations where convention demands it (OHLCV).
1.7.6. Error types: end in Error (e.g. DataGapError, StreamConnectionError,
OrderSubmissionError). Each error type maps to exactly one failure category; generic error
wrapping is acceptable at boundaries but must not replace specific typed errors in
domain-critical paths.
1.7.7. Trading domain vocabulary: OHLCVBar (not CandleStick); RegimeState (not MarketState);
AlpacaClient (not TradeClient); FillPrice (not ExecutionPrice); PositionWeight (not
Allocation).

1.8. C++ Naming Conventions
1.8.1. Classes and types: PascalCase inside the xquantx:: namespace hierarchy
(e.g. xquantx::kernel::KalmanFilter, xquantx::schema::OHLCVBar,
xquantx::earth::MeanVariancePortfolioOperator, xquantx::air::RiskParityOperator). The
namespace prefix is always included in header declarations; never rely on using namespace
to resolve names in headers.
1.8.2. Member variables: snake_case with a trailing underscore for private members
(e.g. state_vector_, covariance_, regime_id_, signal_score_). The trailing underscore
distinguishes private members from local variables and function parameters at a glance.
1.8.3. Functions and methods: snake_case (e.g. update_kalman_state, compute_covariance,
apply_risk_verdict, compute_signal_score). Method names begin with a verb; property-like
accessors use get_ / set_ prefixes.
1.8.4. Constants: k prefix for class-scoped compile-time constants
(e.g. kDefaultWindowSize, kMaxStateDimension); SCREAMING_SNAKE_CASE for file- or
namespace-scoped constants (e.g. MAX_STATE_DIMENSION, DEFAULT_LOOKBACK_BARS).
1.8.5. Namespaces: all lowercase (xquantx, earth, air, fire, water, kernel). No using
namespace xquantx; in any header file. In .cpp files, using declarations for specific types
are acceptable within function or block scope.
1.8.6. Template parameters: single uppercase letter for type-only parameters (T, U);
PascalCase for semantically meaningful parameter names (StateVector, CovarianceMatrix,
ReturnType).
1.8.7. Trading domain vocabulary: OhlcvBar (abbreviated acronym: only first letter uppercase,
remainder lowercase after the all-caps abbreviation boundary); KalmanStateVector;
CovarianceMatrix; RiskVerdict (enum class with values Allow, Reduce, Block, Flatten in C++).

1.9. Rust Naming Conventions
1.9.1. Functions and variables: snake_case (e.g. serialize_ohlcv_bar, process_fill,
compute_signal_score, apply_risk_verdict). Function names begin with a verb; variable names
are descriptive nouns.
1.9.2. Types (structs, enums, traits): PascalCase (e.g. OhlcvBar, RegimeState, DataOperator
trait, SignalScore, AllocationVector). Type names describe the concept, not the
implementation mechanism.
1.9.3. Constants and statics: SCREAMING_SNAKE_CASE (e.g. MAX_BUFFER_SIZE,
DEFAULT_RETRY_COUNT, KELLY_FRACTION_CAP). Constants are declared with const or static in
the module or crate root where they configure behavior.
1.9.4. Modules: snake_case (e.g. mod pipeline; mod serialize; mod schema; mod ohlcv).
Module names mirror file names; the module tree is declared in lib.rs or mod.rs.
1.9.5. Crate names: kebab-case in Cargo.toml (e.g. xquantx-pipeline, xquantx-serialize,
xquantx-schema). The crate name in Rust source uses the underscore equivalent
(xquantx_pipeline, xquantx_schema) for use declarations.
1.9.6. Trait names: PascalCase plus descriptive (e.g. DataOperator, Serialize, Deserialize,
RegimeInference). Traits describe a capability or contract; they are named as nouns or
adjectives, not as verb phrases.
1.9.7. Trading domain vocabulary: OhlcvBar (struct); RiskVerdict (enum with variants Allow,
Reduce, Block, Flatten in Rust); fill_price (snake_case struct field); signal_score
(snake_case field); regime_id (snake_case field matching Python and schema definitions).

1.10. Cross-Language Consistency Rules
1.10.1. Canonical schema field names are defined in snake_case and must be identical across
Python (xquantx.schemas), Rust (xquantx-schema), and JSON serialization boundaries. Go
exported field names use the direct CamelCase equivalent (avg_entry_price -> AvgEntryPrice).
C++ private member variables append a trailing underscore (avg_entry_price_). These
transformations are mechanical and reversible; the canonical snake_case name is the
authoritative form.
1.10.2. Regime identifiers are always the string codes R01 through R12 as defined in
025_xquantx_scenario_catalog.txt. No language binding substitutes integer ordinals, enum
values, or locally invented string codes as the primary regime identifier at schema
boundaries. The regime_id field in all languages stores exactly these string codes.
1.10.3. Operator type names are consistent across languages. MomentumSignalOperator is the
class name in Python, the struct name in Rust and C++, and the type name in Go. The
Operator suffix is preserved in all four languages.
1.10.4. RiskVerdict values are ALLOW, REDUCE, BLOCK, FLATTEN in all languages. Python and
Rust use these as enum variant names. Go uses exported CamelCase constants (Allow, Reduce,
Block, Flatten) or a typed constant group. C++ uses an enum class with the same names. No
language binding invents alternative verdict names.

1.11. File Naming Conventions
1.11.1. Python: snake_case.py for all source files
(e.g. momentum_signal_operator.py, kalman_regime_operator.py,
mean_variance_portfolio_operator.py, earth_agent.py).
1.11.2. Go: snake_case.go for all source files
(e.g. stream_handler.go, order_submitter.go, ohlcv_bar.go). Test files follow Go convention:
stream_handler_test.go.
1.11.3. C++: snake_case.h for headers, snake_case.cpp for implementations
(e.g. kalman_filter.h, kalman_filter.cpp, ohlcv_bar.h, mean_variance_optimizer.cpp).
1.11.4. Rust: snake_case.rs for all module files
(e.g. pipeline.rs, serialize.rs, ohlcv_bar.rs). Module files match their mod declarations
exactly.
1.11.5. Spec files: NNN_xquantx_description.txt using the corpus three-digit numeric prefix
convention (e.g. 023_xquantx_modules_imports.txt, 024_xquantx_naming_conventions.txt). The
prefix is zero-padded to three digits; description words are separated by underscores.
1.11.6. Schema files: snake_case.json in the schemas/ directory
(e.g. ohlcv_bar.json, portfolio_snapshot.json, structured_log_entry.json). Schema file
names match the Python dataclass name in snake_case.

1.16. Conclusion
The X Quant X naming conventions extend language-idiomatic best practices with a
cross-language consistency layer that keeps schema field names, operator type names, regime
identifiers, and verdict values unambiguous across Python, Go, C++, and Rust. The Operator
and Agent suffix rules make abstraction layers legible from class names alone. The trading
domain vocabulary standards prevent synonym proliferation that would otherwise obscure data
lineage across the platform DAG.
