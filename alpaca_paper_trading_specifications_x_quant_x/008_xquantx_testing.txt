1.1. Abstract
This document defines the multi-layer testing strategy for X Quant X across all four
implementation languages (Python, Go, C++, Rust). It specifies four testing layers (unit,
integration, simulation, performance), test taxonomy by language, operator contract testing,
regime-matrix validation, and the Shadow CI gate definition.

1.2. Key Words
testing strategy, unit tests, integration tests, simulation tests, performance tests, pytest,
go test, ctest, cargo test, operator contract, temporal leakage, regime-matrix validation,
Shadow CI gate, property-based testing.

1.3. Executive Summary
X Quant X employs four testing layers: (1) unit tests verifying each Operator in isolation,
including property-based tests for financial invariants; (2) integration tests verifying
Operator chains and Alpaca sandbox API calls; (3) simulation tests running full backtest
cycles with regime-matrix validation; (4) performance tests asserting order submission
latency and throughput. CI runs all four layers on every merge across all four languages.
No merge to main passes unless all language gates are green.

1.4. Key Findings
1.4.1. Unit tests achieve 100% branch coverage on all Operator implementations (per
009_xquantx_unit_tests.txt). Property-based tests (Python hypothesis, Go rapid) assert
financial invariants such as signal_score in [-1, 1] and
regime_probabilities.sum() approximately equal to 1.0.
1.4.2. Integration tests verify Operator chains: DataOperator -> FeatureOperator ->
MarketRegimeOperator -> SignalOperator -> RiskOperator. A separate Alpaca sandbox
integration test verifies that AlpacaPaperExecutionOperator correctly submits orders to
the Alpaca paper endpoint.
1.4.3. Simulation tests run full backtest cycles on the historical dataset with four-variant
regime-matrix validation: {paper, backtest} x {normal_regime, stress_regime}. The temporal
leakage invariant is asserted in every simulation run.
1.4.4. Performance tests enforce: order submission latency <= 200ms (P99, paper mode),
market data ingestion throughput >= 1,000 daily bars/second (backtest mode), per-operator
execution time <= 50ms (P99, paper mode).
1.4.5. Shadow CI gate: a mandatory CI step that runs the full pipeline in Dry-run mode
against the last 5 trading days of live market data, comparing results against a pinned
baseline output. Any divergence from the baseline is a CI failure.

1.5. Philosophical Preamble
A trading system that is not tested at the simulation layer is not a trading system — it is
a hypothesis. Testing in X Quant X is not a quality checkbox after development; it is the
mechanism by which the Temporal Leakage Invariant, the risk-gate verdict coverage, and the
Operator composition algebra are enforced in code. Every new Operator added to the platform
must arrive with its unit test before its first integration test is written.

1.6. Testing Layers
1.6.1. Unit Tests (per 009_xquantx_unit_tests.txt): each Operator in isolation, with 100%
branch coverage. Includes property-based tests for financial invariants.
1.6.2. Integration Tests (per 011_xquantx_integration_tests.txt): Operator chain tests and
Alpaca sandbox API tests.
1.6.3. Simulation Tests (per 013_xquantx_end2end_testing.txt): full backtest cycle with
regime-matrix validation.
1.6.4. Performance Tests (per 012_xquantx_performance_tests.txt): latency, throughput,
memory.

1.7. Test Taxonomy by Language
| Language | Test runner    | Assertion framework         | Property tests | Coverage                  |
|----------|----------------|-----------------------------|----------------|---------------------------|

1.8. Operator Contract Testing
Every Operator implementation is tested against the base Operator contract:
1.8.1. process(valid_inputs) returns a valid OperatorOutputs (schema-validated).
1.8.2. validate_inputs(invalid_inputs) returns a ValidationResult with errors (not raises).
1.8.3. schema_version() returns a semver string matching the operator's declared version.
1.8.4. operator_id() returns a stable, unique string that does not change between runs.
1.8.5. For SignalOperator: output signal_score in [-1, 1] for all valid inputs (property
test).
1.8.6. For RiskOperator: output verdict in {ALLOW, REDUCE, BLOCK, FLATTEN} for all inputs
(property test with all four verdict paths covered).
1.8.7. For MarketRegimeOperator: output regime_probabilities.values() sum to 1.0 +/- 1e-9
(property test).

1.9. Regime-Matrix Validation
The regime-matrix validation runs four variants of the simulation test:
1.9.1. paper x normal_regime: Dry-run mode against recent live data in R01/R02 regime.
1.9.2. paper x stress_regime: Dry-run mode with historical R04/R07 regime period replayed.
1.9.3. backtest x normal_regime: full backtest on normal-regime historical period.
1.9.4. backtest x stress_regime: full backtest on stress-regime historical period.
All four variants must pass for the CI to be green.

1.10. Shadow CI Gate
1.10.1. The Shadow CI gate runs after all other CI steps.
1.10.2. It starts a Dry-run mode session against the last 5 trading days of live Alpaca data.
1.10.3. It compares the session's AUDIT_LOGS/ output to a pinned baseline (stored in
tests/baselines/).
1.10.4. Any divergence in signal scores, risk-gate verdicts, or regime state sequences
(beyond floating-point tolerance of 1e-9) is a CI failure requiring human review.

1.13. Risk and Mitigation Table
| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Unit tests omit branch coverage for a BLOCK verdict path | Medium | High | CI coverage gate requires 100% branch on RiskOperator; untested branches fail CI |
| Temporal leakage not detected in simulation test | Medium | Critical | §1.9 simulation tests include explicit temporal leakage assertion (strictly_increasing_timestamps) |
| Shadow CI baseline becomes stale | High | Medium | Baseline is a versioned file in tests/baselines/; updated deliberately on intentional behavior change |
| Go or C++ tests skipped in CI to save time | Medium | High | §1.7: all four language test runners are mandatory CI steps; none may be marked optional |

1.15. Conclusion
The four-layer testing strategy (unit, integration, simulation, performance) combined with the
Shadow CI gate ensures that every Operator implementation is verified in isolation, in
composition, and against live market data before merging. No layer is optional; all four
language runners are mandatory CI steps. The Shadow CI gate is the final defense against
undetected behavioral regressions.
