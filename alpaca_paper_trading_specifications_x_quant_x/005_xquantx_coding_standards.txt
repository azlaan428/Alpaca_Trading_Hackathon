1.1. Abstract
This document defines the multi-language coding standards for the X Quant X platform — a
Python/Go/C++/Rust quantitative paper-trading system using the Alpaca API. It expands the
original baseline directive (preserved verbatim in Section 1.6) into a full four-language
standard governing Operators, Agents, and shared interfaces throughout the platform.

1.2. Key Words
SOLID, ACID, JPL Power of Ten, Clean Code, modularization, type hints, PEP 8, logging,
constants, configuration, version control, CI/CD, entry point, docstrings, complexity
analysis, Operator interface, Agent composition, Python, Go, C++, Rust, multi-language,
type safety, financial invariants.

1.3. Executive Summary
All code in this repository must satisfy SOLID, ACID, and NASA/JPL Power-of-Ten-style
discipline across all four languages (Python, Go, C++, Rust). Python governs ML, research,
orchestration, and Alpaca API calls. Go governs APIs, services, and low-latency streaming.
C++ governs performance-critical numerical kernels (Kalman filter, covariance matrices,
options pricing). Rust governs high-integrity concurrent data-pipeline components and
serialization. Every Operator is a typed software object implementing a formal interface. No
global variables, no magic numbers, no hardcoded strings or paths. Use structured logging
(never print). Document every function/method with WHAT/WHY/HOW/args/throws/returns/time-
and-space-complexity. The entry point in every language file is minimal and gated. CI/CD
enforces standards across all four language layers.

1.4. Key Findings
1.4.1. The original baseline directive (Section 1.6) is the authoritative seed for this
document and has been preserved verbatim, then extended into four language-specific sections
below.
1.4.2. Every Python file that is directly executable exposes a main() function gated by
`if __name__ == "__main__": main()`, with no other top-level executable code.
1.4.3. Every Go package exposes a clear public API; internal implementation details use
package-private naming; the `main` package is minimal and delegates immediately to a Run()
or Execute() function.
1.4.4. Every C++ translation unit declares its public interface in a header file separate
from its implementation; all numerical operations use double-precision floating point with
explicit precision documentation.
1.4.5. Every Rust crate uses typed error propagation (Result<T, E>); panics are reserved
for programmer errors only, never for recoverable runtime conditions.
1.4.6. This document is upstream of 006_xquantx_scaffolding.txt, 007_xquantx_virtual_env.txt,
019_xquantx_data_structures_algorithms.txt, 023_xquantx_modules_imports.txt, and
024_xquantx_naming_conventions.txt.

1.5. Philosophical Preamble
Code is documentation that executes, and documentation is code that persuades; both fail
under the same conditions — hidden state, unexplained magic values, and untraceable
decisions. X Quant X's Operators and Agents must be as auditable as their own specification
corpus, because a risk-gated trading system whose backend cannot be trusted to compute a
verdict deterministically and traceably has failed its own reason for existing: an
ALLOW/REDUCE/BLOCK/FLATTEN verdict from a RiskOperator is only meaningful if the code path
producing it is inspectable and free of hidden state.

1.6. Original Baseline Directive (Preserved Verbatim)
"SOLID, ACID, JPL 10 FP, Clean Code, modularized codes, no single file doing too much. Def
main only a few lines of code. Documentation with WHAT, WHY, HOW, args, throws, returns, Time
and Space complexity analysis. For python specifically: if __name__ == "__main__": main()
should be the only code outside of functions and classes. No global variables, no magic
numbers, no hardcoded strings, no hardcoded paths. Use constants and configuration files. Use
type hints for function arguments and return types. Use logging instead of print statements.
Write unit tests for all functions and classes. Use virtual environments for dependencies.
Follow PEP 8 style guide for Python code. The entry point must be only a few lines of raw
code. Every python file must have it. Likewise, other programming languages all follow this
example where appropriate. Use version control (git) with meaningful commit messages. Use
branching strategies for features, bug fixes, and releases. Write clear and concise commit
messages. Use code reviews to maintain code quality. Use continuous integration and continuous
deployment (CI/CD) pipelines for automated testing and deployment."

1.7. Structural Discipline (SOLID / ACID / JPL Power of Ten / Clean Code)
1.7.1. SOLID (Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation,
Dependency Inversion) governs Operator and Agent class design: MarketRegimeOperator infers
regime state and nothing else; SignalOperator generates signals and nothing else; RiskOperator
evaluates rule compliance and nothing else — combining responsibilities violates Single
Responsibility.
1.7.2. ACID (Atomicity, Consistency, Isolation, Durability) governs any persistence operation
(trade log, position history, audit trail; see persistence layer in services/).
1.7.3. NASA/JPL Power-of-Ten-style discipline governs defensive coding: bounded loops, no
uncontrolled recursion, simple control flow, and checked return values — especially important
in the numerical kernel where unbounded iteration in matrix inversion can produce silent NaN
propagation.
1.7.4. Modularization: no single file or function performs more than one clearly named
responsibility; see 023_xquantx_modules_imports.txt for module boundary definitions.

1.8. Entry Point and Documentation Discipline
1.8.1. Python: every executable file guards execution with `if __name__ == "__main__": main()`
and no other top-level code outside functions and classes.
1.8.2. Go: every `main` package delegates to a named function (e.g. `Run()`) within a few
lines; the `main()` function itself sets up logging and calls `Run()` only.
1.8.3. C++: every executable translation unit has a `main()` of <= 20 lines that parses
arguments and delegates to a named class or function.
1.8.4. Rust: every binary crate has a `main()` of <= 20 lines; all logic is in library crate
functions called from `main()`.
1.8.5. Every function, method, and class docstring records: WHAT the unit does, WHY it
exists, HOW it accomplishes its purpose, its Args, any exceptions it Raises, its Returns, and
a Complexity: line stating time and space complexity in Big-O notation. Example:
`compute_kalman_update(state: KalmanState, observation: f64) -> KalmanState` documents that
it is a pure function with no side effects, O(n^2) in state dimension.

1.9. Language-Specific Rules
1.9.1. Python rules: No global variables (shared state is in a context object like
`SessionContext`); no magic numbers or hardcoded strings/paths (use constants and config
files); type hints mandatory on all signatures (per 024_xquantx_naming_conventions.txt); use
`logging` module exclusively (`print()` disallowed outside throwaway debugging); PEP 8
mandatory; dependencies in virtual environment (per 007_xquantx_virtual_env.txt); `mypy
--strict` must pass.
1.9.2. Go rules: All exported identifiers have documentation comments; errors are returned,
not panicked (except truly unrecoverable programmer errors); goroutines are documented with
their lifetime and cancellation mechanism; no naked `interface{}` (use typed interfaces);
`go vet` and `golangci-lint` must pass.
1.9.3. C++ rules: All headers use `#pragma once` or include guards; all numerical results are
checked for NaN/Inf before propagation; no raw pointers in new code (use smart pointers);
`clang-tidy` must pass; all floating-point arithmetic is IEEE 754 double precision unless
explicitly documented otherwise.
1.9.4. Rust rules: All public items have rustdoc comments; `Result<T, E>` for all fallible
operations; no `unwrap()` or `expect()` in library code; `clippy` must pass at
deny(warnings); no `unsafe` without a documented safety invariant.

1.10. Version Control and CI/CD Discipline
1.10.1. Git is the version-control system; commit messages follow Conventional Commits style.
1.10.2. A branching strategy separates feature, bug-fix, and release branches.
1.10.3. Every change is code-reviewed before merge.
1.10.4. CI/CD pipelines run tests and linters for all four languages on every merge: `pytest`
+ `mypy` (Python), `go test` + `golangci-lint` (Go), `ctest` + `clang-tidy` (C++), `cargo
test` + `clippy` (Rust). No language gate may be bypassed.
